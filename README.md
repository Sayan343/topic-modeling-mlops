# Text Topic Classifier — MLOps Portfolio Project

An LDA-based topic classification model, trained on live current-events data,
served via Flask and Streamlit, on its way to a full containerized AWS
deployment with CI/CD.

**Live demo:** _(Streamlit Cloud link — coming soon)_
**Status:** Core model + local serving complete. Docker and AWS deployment in progress.

---

## The problem this solves

Manually tagging incoming text — support tickets, news articles, customer
feedback, forum posts — by subject is slow and doesn't scale. This project
automatically classifies a piece of text into a topic (e.g. business, tech,
sports, health, politics) so it can be routed, filtered, or organized without
a human reading every item first.

**Input:** any piece of text
**Output:** a predicted topic label, a confidence score, and the keywords
that define that topic

```json
// Input
{"text": "The central bank raised interest rates to combat inflation"}

// Output
{
  "topic_id": 3,
  "topic_label": "prices, ai, oil prices",
  "keywords": ["prices", "ai", "oil prices", "treasury", "raised", "amid", "industry"],
  "confidence": 0.812
}
```

---

## How it works

1. **Data collection** (`fetch_modern_data.py`) — pulls current articles from
   9 public RSS feeds (BBC News/Business/Tech/Health, TechCrunch, ESPN, NPR,
   Al Jazeera, CNBC), giving a live, current-events training corpus instead
   of a static historical dataset.
2. **Model training** (`train_model.py`) — trains an LDA (Latent Dirichlet
   Allocation) topic model with:
   - An extended stopword list to filter informal filler words
   - Bigrams (two-word phrases like "tax reform", "oil prices") for more
     specific, meaningful topic keywords
   - Topic count auto-scaled to corpus size (fewer documents → fewer topics,
     to avoid muddled, overlapping clusters)
3. **Serving** — two interfaces over the same trained model:
   - `app.py` — a Flask REST API (`/health`, `/predict`)
   - `streamlit_app.py` — a visual web UI with example buttons, confidence
     charts, and a documented limitations section

## Real test results

Tested against a range of inputs, from clean single-topic text to
deliberately complex, multi-theme articles:

| Input type | Example | Result |
|---|---|---|
| Clear single-topic | "The basketball team won the championship" | Correctly matched, high confidence |
| Government/tax policy | "New government policy on tax reform" | Correctly matched `tax reform` as a bigram, 87% confidence |
| Deliberately mixed (AI + energy + policy) | Multi-topic paragraph blending AI investment, energy demand, and tax policy | 33% confidence, split across `oil, deal, ai` — appropriately uncertain rather than falsely confident |
| Deliberately mixed (sports + business + health) | Paragraph on athlete contracts, concussion protocols, and streaming rights | 50% confidence on `news, google, life, ai` instead of a sports topic |

That last result surfaced a genuine, specific limitation (see below) rather
than a generic "the model isn't perfect" disclaimer.

---

## Known limitations

- **Sports topic is soccer-anchored.** Training RSS sources (BBC, Al
  Jazeera) skew UK/international, so the model's sports vocabulary is built
  from soccer/football terms. Text about American football, baseball, etc.
  shares little vocabulary overlap and gets misclassified. This is a direct,
  traceable consequence of RSS source selection, not a modeling flaw — a
  production system would need geographically/topically balanced sources.
- **Small training corpus (~270 documents).** Some topics can be dominated
  by a single trending headline rather than a broad recurring theme. A
  larger, multi-day corpus would smooth this out.
- **Confidence drops on genuinely mixed-topic text.** This is expected,
  correct behavior for a probabilistic model — a single overconfident label
  on ambiguous text would be the actual red flag.
- **No formal coherence metric yet.** Topic quality has been evaluated by
  manual inspection of keywords and test predictions, not a quantitative
  score (e.g. topic coherence). This is a planned addition.

## Running it locally

```bash
pip install -r requirements.txt
python fetch_modern_data.py     # collects current RSS articles
python train_model.py           # trains the model on that data
python app.py                   # Flask API on localhost:5000
# or:
streamlit run streamlit_app.py  # visual UI on localhost:8501
```

Test the Flask API:
```bash
curl -X POST http://localhost:5000/predict \
  -H "Content-Type: application/json" \
  -d '{"text": "the stock market rallied today amid strong earnings"}'
```

## Next steps (in progress)

### Docker containerization
The `Dockerfile` is written (Flask app served via Gunicorn) but not yet
built/tested. Next: confirm `docker build` and `docker run` work correctly
with the current model artifacts, then push the image to AWS ECR.

### AWS deployment
Planned architecture, matching a standard MLOps deployment reference design:
- **ECR** — Docker image registry
- **ECS + Application Load Balancer** — container hosting with a public endpoint
- **CodeCommit + CodeBuild + CodePipeline** — CI/CD so a code push triggers
  an automatic rebuild and redeploy

**Cost discipline:** since this is a student project, a AWS Budgets alarm is
set at $1 before any billed resource is created, and ECS/ALB resources are
torn down promptly after testing and screenshotting — this project is not
kept permanently running on AWS to avoid ongoing charges. Screenshots and a
recorded demo substitute for a permanently-live AWS endpoint; the
permanently-live demo link is the Streamlit Cloud deployment instead.

### Planned quality improvements
- Topic coherence score (quantify topic quality, not just eyeball it)
- Larger training corpus (combine multiple days of RSS collection)
- Unit tests for the Flask API's input validation
- GitHub Actions CI to build/test on every push (a free, always-visible
  complement to the AWS CodePipeline work)

## Why LDA (and not a transformer-based approach)

LDA was chosen for this project because it's interpretable, has no GPU
requirement, and installs cleanly across platforms — relevant constraints
for a student project with no dedicated infrastructure budget. A modern
alternative worth comparing against is
[BERTopic](https://maartengr.github.io/BERTopic/), which uses sentence
embeddings and typically produces more semantically coherent topics on
short text, at the cost of a heavier dependency chain (sentence-transformers,
UMAP, HDBSCAN) and no GPU means slower training. This trade-off — and the
decision process behind it — is intentional and documented here rather than
left unexamined.
